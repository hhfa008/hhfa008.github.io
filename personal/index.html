Selected work

Three programs, one method: measure first, then change one thing.

These three programs come from full-time iOS platform roles held between 2020 and 2026. They are employment track record, not paid consulting engagements. Each is written as problem → what I did → measured result, with the metric definition kept in the text.

Anonymized: client and product names, internal codenames, exact business metrics, absolute OOM baselines and sample sizes, and exact project dates. Not anonymized: the problem, the measurement definition, the tooling category, the role, and the relative change. No client testimonial is published here.

01

OOM and memory on a top short-video platform

iOS · short-video and live app · consumer scale

Measurement: in-house per-screen footprint sampler; the last run’s scene stack, footprint, and thread count persisted and reported on the next launch; OOM exits per session on low-tier devices.

Problem

Out-of-memory exits were rising faster than crash reports suggested. The team could see that a session had died, but not which screen was open, how much memory it held, or which asset pushed it over the limit.

What I did

Made memory attributable: sampled footprint per screen, persisted the last run’s scene stack, footprint, and thread count, and reported it on the next launch, so every OOM had a scene and a number attached.

Result

−3.18% relative OOM rate on low-tier devices
87.9 MB decoded images removed from one startup path
18 → 1.7 MB gift image memory

What this does and does not say: −3.18% is a relative change in OOM exits per session on low-tier devices, not a 3.18-point drop. The absolute baseline, sample size, and exact measurement window are withheld under client confidentiality.

02

First screen for a live-streaming platform

iOS · live streaming · viewer path

Measurement: segmented first-screen instrumentation (app preparation, player pre-render, stream pull, surface wait); the same definition in lab and production; click-to-first-frame from a fixed replay on a mid-tier device.

Problem

Entering a live room felt slow even when the dashboard said it was fine. First screen was measured as one number, so app preparation, player pre-render, and the stream pull were mixed together.

What I did

Split the path into segments — app preparation, player pre-render, stream pull, and surface wait — and instrumented each one, so lab runs and production used the same definition.

Result

−166 ms total first-screen time (−18%)
−162 ms pre-render time (−73%)
732 → 126 ms click-to-first-frame in the lab (−82%)

Metric definition: first screen runs from room entry to the first rendered frame. The lab figure is from a fixed replay on a mid-tier device; production figures use the same segment definitions. Absolute production baselines are withheld.

03

720p at 30fps on a live-streaming platform

iOS · live streaming · playback and overlays

Measurement: release build, fixed 720p30 room replay, one variable toggled per run, ten runs per case, percentiles instead of averages; GPU cost measured against a 12% baseline.

Problem

Moving live rooms to 720p at 30fps raised GPU and CPU pressure. Overlays — comments, gifts, floating hearts, gift slots, comment aggregation — shipped feature by feature, and nobody knew which one was eating the frame budget.

What I did

Built a repeatable 720p30 harness: release build, fixed room replay, clean background, one variable toggled at a time, ten runs per case, and percentiles instead of averages.

Result

+21 points GPU cost with all overlays on, against a 12% baseline
+10 / +8 / +7 points for gift slots, comments, floating hearts
+15 points for the four overlays measured together

What this does and does not say: this is a cost measurement, not a claim that GPU use fell. The deliverable was a per-overlay budget and a device-tier degradation ladder. Per-device frame-rate outcomes are withheld under client confidentiality, so I do not claim that 30fps was held on every low-tier device.
