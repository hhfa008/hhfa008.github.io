Every number on this page is an estimate. The figures come from the formulas shown below, not from a measurement of your encoder, network, or device. Treat them as planning inputs, then verify against your own pipeline.

Formulas and assumptions — open to check the math

Frame budget

budget_ms = 1000 / fps

The time each frame may spend in an encode step before the next frame is due.

Bitrate

Mbps = width × height × fps × bpp / 1,000,000

A coarse planning estimate. Screen content with large static regions can cost far less; noise, motion, and 4:4:4 chroma can cost more.

Max fps at full resolution

max_fps = bandwidth_bps / (width × height × bpp)

Column A holds the input resolution and solves for the frame rate the link can carry.

Downscale factor

scale = √( bandwidth_bps / (width × height × fps × bpp) )

Column B holds the target frame rate and solves for the pixel count. The linear scale is the square root of the area ratio.

Encode-fit scale

scale_enc = √( 2,073,600 × (budget_ms / base_ms)^(1 / 0.85) / pixels )

Column B takes the smaller of the bandwidth scale and the encode-fit scale, so the target frame rate also fits the encoder. If the input already fits, the scale is capped at 100%.

Encode time

t ≈ base_ms × (pixels / 2,073,600)^0.85

Planning estimate for a hardware encoder. Base at 1080p: H.264 5 ms, HEVC 8 ms, AV1 11 ms. Device, preset, content, and thermal state move this a lot.

Decode time

decode ≈ 0.6 × encode

A rough asymmetry factor; hardware decoders usually run ahead of encoders.

Total latency

capture + encode + RTT/2 + 2 × frame + decode + render

Capture is one frame interval. Network is one one-way trip. Jitter buffer is two frames. Render is 16.7 ms for a 60 Hz display.

bpp assumptions

H.264 0.08–0.14 · HEVC 0.05–0.09 · AV1 0.035–0.07

Bits per pixel per frame. The calculator uses the midpoint for single-value outputs and the ends of the range for the bitrate band.

  • These are estimates, not measurements. No encoder, device, or network is benchmarked here.
  • The bpp bands are planning assumptions for interactive video and screen content. They are not codec guarantees and do not include rate-control behavior.
  • Encode and decode times assume hardware acceleration. AV1 in particular may fall back to software, where encode time can be several times higher.
  • Column A is capped by the lower of the bandwidth limit and the encoder throughput (1000 / encode time). Column B downscales until both the bitrate and the per-frame encode time fit.
  • Network latency is modeled as RTT ÷ 2, with no retransmission, queueing, or congestion. Wi-Fi, relays, and busy uplinks add real delay.
  • The jitter buffer is fixed at two frames. Real implementations often use one to five frames, or adapt the buffer at runtime.
  • The 150 ms line is a common interactive reference, not a requirement. Cloud gaming often targets lower; remote support and presentations tolerate higher.
  • Raising the frame rate shrinks the frame-interval and jitter terms but increases the bitrate. Lowering the frame rate does the opposite.
