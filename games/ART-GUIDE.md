# 制图经验（ART）

> 记录时间：2026-11-10
> 适用：`games/assets/art/`、`scripts/art/`、`games/assets/art/decks/`
> 一句话：**AI 只画单个物件，字符和局面由代码算。**

---

## 0. 最重要的一条：配图是「真实成立的局面」，不是氛围图

第一版做出来的是好看但不成立的图：象棋空盘上两枚子、围棋九路却画 19×19 盘、麻将只有 3 张、双陆只有 6 枚。用户一句「这是常识」就否了。

**动手前先列该物品的真实规则清单**：件数、摆法、尺寸、区分方式。列完再生成。

---

## 1. 分工：谁能画什么

| 内容 | 谁来做 | 原因 |
|---|---|---|
| 单个物件（棋子、牌面载体、筹码、骰子） | AI 生成 | 材质、光影、磨损这些细节模型强 |
| 字符（帥／萬／♠／A／10） | **代码用系统字体渲染** | 模型画中文与花色必出乱码或变形 |
| 完整局面（32 枚象棋、13 张麻将） | 代码合成 | 件数、位置、透视必须可控可校验 |
| 花色形状 | **标准 SVG 路径** | AI 画的黑桃「底宽柄短」，不是标准形 |

字体实测：`Songti SC` 的 **Black(900) 缺 `帥將馬車砲萬東發`**，只有 **Bold(700)** 全覆盖。按「越粗越好」选 900 会静默掉字。

## 2. 单元素生成规格

- 背景**纯白 #FFFFFF**，无环境、无投影、无地面
- 单一物件居中，四周留 ≥12% 白边
- 光照**左上**，产品摄影口径：`100mm macro, f/11, 大柔光箱 + 右侧补光`，要有材质微观纹理（木棕眼、漆面橘皮纹、纸纤维、黏土麻点），不能是 CG 的过分干净
- 输出 **1024×1024**
- 除必要字符外，画面禁止任何文字、字母、数字、logo、水印

**必须写进提示词的真实尺寸**（见下表），否则模型给的比例是随机的。

## 3. 真实尺寸表（1mm = 8px @1024，4px/mm @512）

| 物件 | 规格 |
|---|---|
| 国际象棋王／后／象／马／车／兵 | 95 / 82 / 70 / 62 / 55 / 45 mm 高，底座 Ø30–35mm |
| 中国象棋 | Ø30mm、厚 10mm |
| 围棋子 | Ø22mm、厚 10mm |
| 麻将牌 | 26mm 高 × 19mm 宽 × 16mm 厚 |
| 扑克牌 | 63×88mm，300gsm |
| 筹码 | Ø39mm、11.5g |
| 骰子 | 16mm |
| 四子棋圆片 | Ø32mm |
| 黑白棋 | Ø30mm |
| 跳棋／双陆 | Ø30mm／Ø25mm |

导出按比例尺归一，**不要把所有元素统一缩到同一个最长边**——那样王和兵一样大。

王/兵 比例核对：95/45 = **2.11×**（曾误写成 1.7×，实测 2.12× 才对）。

验收：实际像素高度与应得值差值应 ≤ ±5%（我们实测统一 −1%，来源是抠图每边腐蚀 1px）。

## 4. 抠图：**不要用 colorkey**

`ffmpeg colorkey=0xFFFFFF` 会把物件内部的白色一起抠穿。实测 alpha 保留率：

| 元素 | colorkey 后保留 |
|---|---|
| chip-black | **50.1%** |
| go-stone-white | 73.1% |
| card-face-blank | 82.1% |
| reversi-white | 83.7% |

正确做法：**四角洪水填充 + 1px 腐蚀**，只删与画面边缘连通的纯白底。

**验收判据不是四角 alpha=0**——colorkey 也能满足，会误报通过。必须查**内部像素**：

```bash
ffmpeg -i out.png -vf "crop=1:1:512:512,format=rgba" -f rawvideo - | od -An -tu1
# 第 4 字节（alpha）必须为 255
```

## 5. 现实规则清单（每类物品的身份靠什么区分）

| 游戏 | 区分方式 | 易错点 |
|---|---|---|
| 中国象棋 | **字色**（同一浅木载体，红方红字、黑方黑字） | 做成「整枚红漆/整枚黑漆」是错的 |
| 围棋 | **材质**（那智黑石 / 蛤碁石） | — |
| 国际象棋 | 木色（浅枫木 / 深胡桃） | 12 枚必须像同一副，同相机、同底座 |
| 跳棋 / 双陆 | 棋色（深 / 浅两种） | 只有一边颜色会变成「一方对空盘」 |
| 黑白棋 | 同一枚棋子的两面 | — |
| 四子棋 | 塑料色（红 / 黄） | — |

**扑克**（最容易想当然）：
- J/Q/K 是**左右镜像的半身人像**，不是把字母放进花边方框
- 2–10 点阵**上下旋转 180° 严格对称**：4 四角、5 四角+正中、6 两列各三、7 加中上、8 加中上下、9 两列各四+正中、10 加中上下
- A 是**单枚大花色 + 装饰**，不是放大的角标
- 角标：左上点数+小花色，右下同内容旋转 180°

**麻将**：筒子是**蓝/绿/红**三色（不是红绿黑），1筒是大圆环；条子绿为主；白板有**蓝绿边框**；万子黑数字 + 红萬。

## 6. 合成：一台相机 + 一个平面

- 相机：`perspective: 1600px`，桌面 `rotateX(52deg) rotateZ(-14deg)`，`preserve-3d`
- 物件分两类：
  - `flat`（牌、麻将、棋子饼、筹码、骰子）→ 贴在桌面平面里，跟透视一起形变
  - `standing`（国际象棋、灯灵）→ 屏幕直立广告牌，按同一相机公式换算位置，**alpha 底边落在桌面点**
- 阴影：每个物件下方一枚椭圆径向渐变，中心在底部、平面内偏移 (6,18)px、`blur(6px)`，**在平面里**跟着透视走。不要各写各的 `box-shadow`
- 棋盘画在平面里：chess8 / go19（九路用 9×9！）/ xiangqi9x10 / reversi8 / connect4frame / backgammon / cardtable，占宽 ≥85%，允许裁出画外

**元素按真实尺寸导出后必须按 alpha 包围盒裁切再 contain 到牌面**，否则 1024 画布里的 23% 小物件直接缩放会缩成一点。

## 7. 校验：能阻断的才算校验

`scenes.json` 每个场景声明：

```json
"realism": { "pieceCount": 32, "mustTouchSurface": true, "board": "chess8" }
```

出图前逐条验证，不满足就 `REALISM FAIL` 并**拒绝出图**（退出码 3、零文件）：

- 件数与规则一致（象棋 32、双陆 15+、跳棋 12+12、麻将 13+牌墙、斗地主 17、德州 5+2）
- 有重力约束的（四子棋）每列必须从底行连续，`column 2 floats: rows 5,4,2 instead of 5..3`
- 布局错误也要拦：后/王对调 → `light back rank: column 3 is king, expected queen`
- 物件不得悬空

## 8. 可复现性：配置和产物必须同一次提交

踩过的坑：只提交了渲染产物、把 `scenes.json` 留在工作区，**干净 checkout 后重跑会得到不同的图**（象棋件数、背景、牌面配置全不一样）。

规矩：
- 改配置 → 立刻重跑 → `git status` 里 `composed/` 必须零变化，才说明图与配置锁死
- 同一份 `scenes.json` + 同一批元素，两次运行**逐字节一致**（我们用 md5 对比 25 个 PNG）

## 9. 体积与仓库

| 项 | 预算 | 现状 |
|---|---|---|
| 单张 OG（1200×630） | ≤ 200KB | 约 530–790KB（PNG，未压） |
| 单张 card（480×320） | ≤ 60KB | 约 130–180KB |
| 牌组 WebP | ≤ 30KB/张、总量 ≤ 3MB | 1.11MB，单张最大 14.7KB |
| 元素 @2x | — | 1024 透明 PNG |

- **PNG 母版入库保留**（要重压/重上色靠它），WebP 供站点引用
- 大文件走 **Git LFS**（`*.png *.webp`）；mac2 没有 `git-lfs-authenticate`，所以**代码走 git（`GIT_LFS_SKIP_PUSH=1`）、图片走 rsync** 到 `~/hhfa008-art`
